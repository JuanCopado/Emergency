## Safety/integrity properties

1. Binary interpretation is impossible until required metadata/privacy and burned-in-identifier checks are explicitly completed.
2. A configured provider must use HTTPS.
3. Provider redirects are rejected.
4. Provider response size is capped.
5. The provider receives a generic source filename rather than the original filename.
6. The provider does not receive the source SHA-256; the hash remains an internal integrity/provenance reference.
7. Prepared-upload payloads are HMAC-signed by the trusted backend; tampering with privacy state, routing or other prepared metadata fails closed.
8. The original binary remains non-retained by the local API.
9. The provider result is a proposal only: `review_required=true`, `persisted=false`.
10. Only clinician acceptance persists content into the clinical note.
11. AI-generated image interpretation cannot be mislabeled as an official report. `official_report` is allowed from the provider only for document/PDF extraction; image modalities must use AI interpretation/findings/impression provenance.
12. Provider output is screened again for possible direct identifiers before being returned to the review UI.
13. Confidence remains qualitative only: high/moderate/low/null.

## Provider contract

Runtime configuration:
- `CLINICAL_VISION_PROVIDER_URL` — required to execute a provider call; HTTPS only.
- `CLINICAL_VISION_PROVIDER_TOKEN` — optional bearer token for deployments that use it.
- `CLINICAL_VISION_TIMEOUT_SECONDS` — 1..180 seconds, default 45.
- `CLINICAL_NOTE_PREPARED_HMAC_KEY` — recommended stable deployment key. If absent, the single-process local server generates an ephemeral key; pending prepared uploads become invalid after process restart.

No external provider/model is bundled or silently assumed by the repository. Until a deployment supplies the configured endpoint and credentials, the adapter remains fail-closed rather than inventing image interpretation.

## Central routing

The adapter preserves the existing central module route for each source, including:
- ECG -> `ecg-image`
- chest/radiography -> `clinical-image-interpretation`, `chest-xray`, `musculoskeletal-xray` as appropriate
- CT/MRI -> `ct-mri-screenshot`
- POCUS/ultrasound -> `pocus-image`
- other image/DICOM -> `other-clinical-image`
- PDF/document -> `clinical-note-diagnostic-support`

The route is part of the signed prepared payload and is sent to the configured provider as execution context.

## Frontend behavior

For routed binary sources the MCDT card now:
- displays the privacy review requirements;
- keeps the interpretation button disabled until the required checks are complete;
- invokes the trusted backend adapter;
- displays provider/model/confidence/limitations when returned;
- keeps the result in **Pendente** state after interpretation;
- still requires explicit clinician **Aceitar / Editar / Rejeitar**.
