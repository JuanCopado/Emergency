## Comandos efectivos de CI

### Clinical QA (desde raíz salvo el último comando)

```text
python -m pip install -r clinical/requirements-test.txt
cd clinical
python3 qa/qa_runner.py
```

`requirements-test.txt` incluye `-r requirements.txt`: instala ReportLab 5.0.1, pypdf 6.20.0 y PyYAML 6.0.3, además de dependencias transitivas. ReportLab permanece declarado en runtime; los dos parsers son requisitos de test. No se instala un paquete de PDF ad hoc fuera del contrato.

El runner conserva los seis validadores: módulos, cobertura de evidencia, procedencia de casos clínicos, imágenes reales, fuentes de datasets y plantilla ciega. Ejecuta una vez `python -m unittest discover -s <clinical/tests> -p test_*.py` con su propio intérprete. Esto incluye schemas/registries, notas/exportación Unicode, scores/calculators, procedimientos, evidencia, gotas y metadatos visuales. El paso de 12 a 7 controles agrupa las suites, no elimina cobertura ni relaja los gates humanos.

### App UI QA (working-directory: app)

```text
python -m pip install -r ../clinical/requirements-test.txt
npm ci
npm run guides:test
npm run procedures:test
npm run typecheck
npm test
npm run build
git diff --exit-code -- src/data/generatedClinicalGuides.json src/data/generatedProcedures.json
npm run guides:print-check
```

El build ejecuta `guides:build`, `procedures:build`, `tsc -b` y `vite build`. Las pruebas de fidelidad preceden al build para que una regeneración no oculte un artefacto obsoleto. El último paso usa `CHROMIUM_PATH=/usr/bin/google-chrome`; pypdf se invoca mediante el Python configurado por setup-python. La imagen Ubuntu incluye Chrome según el [inventario oficial de runner-images](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md); la compatibilidad real en ese runner aún requiere ejecución remota.

### Evidence surveillance guardrails (raíz)

```text
python -m compileall -q clinical/scripts clinical/tests
python -m unittest discover -s clinical/tests -p "test_evidence_*.py" -v
```

La segunda línea se ejecuta solo con `workflow_dispatch`. Siempre se ejecuta el bloque Python del workflow que rechaza primitivas `git push`, `merge_pull_request`, `auto_apply=True` y `production_changes_applied=True` en los scripts de vigilancia. En push/PR las 19 pruebas de evidencia están incluidas en Clinical QA.

## Contrato del catálogo

El consumidor real era `relatedProcedures.ts`, usado por la biblioteca clínica general. No existe un consumidor separado del catálogo visual de 158 que justifique otro artefacto. No se crea un duplicado visual ni se altera su índice.

`app/scripts/build-procedures.mjs` genera `generatedProcedures.json`. Toma ID, nombre, familia y nivel del índice maestro; obtiene ruta y encabezado exacto de la ficha canónica. Los alias deben coincidir en índice y fichas, y apuntar directamente a un canónico existente. La generación rechaza IDs duplicados, discrepancias entre inventarios, referencias inexistentes, cadenas de alias y niveles no reconocidos. Ordena por ID con comparación estable y normaliza saltos de línea para Windows/Linux.

Cada canónico contiene `id`, `name`, `family`, `level`, `sourcePath`, `sourceHeading` y `aliases`. No se añaden campos clínicos inferidos. `getCanonicalProcedure(id)` devuelve el mismo objeto y origen para ID canónico o alias; un ID desconocido devuelve `undefined`. No se añaden páginas/rutas de procedimientos nuevas; se proporciona resolución canónica para consumidores y se conserva la presentación existente de relacionados.
