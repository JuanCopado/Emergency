# v1.39 CLINICAL NOTE — TRUSTED API / E2E STATE

Date: 2026-10-06
Branch: `v1.39-clinical-note-diagnostic-support`

## Implemented runtime path

`React UI -> typed API client -> clinical_note_api.py -> privacy gate -> central routing/diagnostic/export modules`

### Upload contract
1. Browser sends one selected file to the trusted backend.
2. Backend limits size, computes SHA-256 and classifies the attachment.
3. Text-like sources may be extracted as text for review.
4. Binary image/PDF/DICOM sources are never guessed/interpreted locally.
5. Direct-identifier detection is STOP.
6. Binary sources require explicit metadata/privacy review and, where applicable, burned-in identifier review.
7. The original binary is not retained by this adapter.
8. The proposed result appears as a review card.
9. Only `Accept` persists reviewed result text into the note.
10. Edit/reject invalidates prior acceptance and clinician validation.

### Diagnostic support
- 92 deterministic syndrome rules remain the central engine.
- Confidence remains qualitative only: high/moderate/low.
- Only accepted note data are analyzed.
- A new diagnostic run resets clinician review.

### Medication safety
- Treatment suggestions are non-actionable by default.
- The API returns a medication-safety gate.
- Structured pediatric outpatient regimens can call the existing executable pediatric medication alert engine.
- Other medication actions remain REVIEW_REQUIRED until a structured central medication-selection safety adapter exists.

### Export
- DOCX/PDF/JSON use the central privacy + clinician-review gate.
- Original uploaded clinical files are not embedded by default.
- Export sections follow the agreed clinical sequence.
- Official reports and AI interpretations are rendered separately with provenance.

## Deliberate boundary
The local stdlib backend is an orchestration/safety layer, not an autonomous medical image model. Actual binary interpretation must be supplied by a trusted deployment adapter wired to the existing central image modules and must still pass clinician accept/edit/reject.

### Filename and red-flag hardening — final v1.39 delta
- upload privacy preflight scans the filename together with any safely extracted text;
- burned-in identifier review is required for binary image/PDF/DICOM media, not for plain-text reports;
- objective diagnostic signals/red flags returned by the central diagnostic engine are exposed in the typed frontend contract and rendered separately from must-not-miss diagnoses;
- engine-suggested active problems are visible as review-required suggestions, not silently merged into the clinician problem list;

## Production vision adapter extension — 06/10/2026
The earlier deliberate boundary has been partially closed: a trusted production-facing adapter now exists and is wired to the API/UI. It is not itself a diagnostic model.

Implemented guarantees:
- binary provider execution occurs only after explicit privacy/burned-in review;
- HTTPS-only configured endpoint;
- HMAC integrity protection for prepared uploads;
- original filename and internal SHA-256 are not disclosed to the provider;
- redirects rejected and provider response size capped;
- provider output direct-identifier scan;
- qualitative confidence only;
- AI image interpretation cannot be stored as an official report;
- result stays unpersisted until clinician acceptance.
